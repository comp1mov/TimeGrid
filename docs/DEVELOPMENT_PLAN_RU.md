## Этап 1 Точка сравнения и сохранность рисунков

Повторить небольшой набор сценариев на 28.34: 24 и 96 ячеек, BG/TPL/FRM, long stroke, gaps, grid/single, zoom/pan, rotation/mirror, onion/reference, undo и прозрачный экспорт. Записать размеры поверхностей до открытия кисти, после открытия и после первого штриха; счётчики geometry reads, время маршрутизации точек и композиции.

Зафиксировать минимальную модель данных рисунка: тип привязки, логическая система координат, идентификатор sample occurrence, растровые assets и история изменённых областей. До смены хранения сделать fixtures и переходный import/export старого sheet, чтобы миграция не уничтожала работы.

Критерий: есть повторяемый desktop baseline и сохранённые эталоны; старый рисунок проходит round-trip без изменения привязки и пикселей. Телефон проверяется отдельной строкой с моделью устройства, ОС, браузером и типом ввода; эмуляция не заменяет этот прогон.

## Этап 2 Быстрые исправления drawing input

Сохранить вид и поведение кистей. Перевести screen → composition → cell в отдельную модель координат. У регулярной сетки вычислять строку и колонку, не обходить DOM для каждой промежуточной точки. Геометрию кэшировать и инвалидировать при изменении layout, viewport, transform и scroll; при сложной геометрии использовать подготовленную карту.

Сначала сохранить различия mouse/touch/pen в адаптерах. Затем свести их к общему потоку точек с временем и доступным pressure, сохранив coalesced samples, pointer capture, отмену и правила multi-touch. Не заменять поведение long stroke одним упрощённым обработчиком.

Не создавать большой пустой FRM-sheet после импорта или открытия панели кисти. Пустой слой должен иметь явное состояние без пиксельного backing. Композицию активного штриха планировать не чаще одного раза за animation frame, при этом входные точки не терять.

Критерии: при неизменной геометрии нет обхода rect всех ячеек на каждую точку; до первого рисунка FRM backing равен нулю; переходы через границы/gaps, undo и экспорт соответствуют эталонам. Сравнить median/p95 с новым baseline без обещания универсального FPS.

## Этап 3 Новое хранение рисунков

- **BG:** логическая поверхность композиции; сохранить существующее различие grid/single.
- **TPL:** рисунок в локальных координатах шаблона, повторяемый в ячейках.
- **FRM:** рисунок привязан к устойчивому ID выбранного вхождения sample, а не к текущей колонке или позиции DOM. Одинаковый исходный кадр в двух вхождениях может иметь разные рисунки, как и сейчас.

Растровые tiles создаются только в затронутых областях. Физический atlas при необходимости служит кэшем для preview/export, но не единственным оригиналом рисунков. Undo хранит изменения tiles с лимитом байтов. Учитываются отдельные бюджеты active stroke, undo, decoded assets и renderer cache.

Смена числа колонок, preview quality или proxy не пересэмплирует оригинал рисунка. При новой выборке несовпавшие drawing assets сохраняются для восстановления, а не молча удаляются. Старые sheet/snapshot форматы читаются через миграционный адаптер.

Dirty-region rendering применяется только там, где результат локален. Эффекты, затрагивающие соседние кадры или всю композицию, явно расширяют область пересчёта. Результат экспорта всегда использует полную требуемую точность.

Критерии: память зависит от реально нарисованных областей; рисунок переживает layout/quality changes и save/reopen; undo, long stroke, стирание, alpha и все привязки сохраняют поведение. Проверить desktop и физический мобильный ввод отдельно.

## Этап 4 ProjectDocument и общий расчёт композиции

Минимальный ProjectDocument объединяет source references, sampling/occurrence IDs, параметры, drawing assets и seed. Runtime-объекты — DOM, canvas, VideoFrame, URLs и caches — в документ не входят.

Первый вертикальный сценарий: импорт → выборка → рисунок/эффект → сохранить → закрыть → открыть/relink → сменить preview quality → экспортировать ту же композицию. Baked reimport из JPEG/MP4 — отдельное обещание: он не восстанавливает скрытые редактируемые слои.

Preview и export получают общий план кадров, геометрии и слоёв на момент T. Затем можно разделять temporal/color/composition passes и кэшировать их независимо, сохраняя проверенный порядок эффектов. Ограничить очередь кодировщика и убрать необходимость заранее держать все полноразмерные кадры для видеоэкспорта.

## Этап 5 Cloud отдельным пилотом

В Cloud-папке уже есть локально проверенные WebCodecs sampling, IndexedDB cache, versioned recipe, общий renderer, ручной bake, API, durable jobs, авторизация сессий и cleanup. Полный effect DAG пока не внедрён: существующая scene composition остаётся одним крупным этапом.

D1 создан, Modal CLI подключён. В Modal пользователь выставил usage limit $30 при $30 compute credits. Modal Volumes не используем. R2 пока не активирован; нужны отдельное решение о подписке, приватный bucket и scoped credentials.

После настройки хранения проверить реальные signed uploads и multipart, D1 claims, повторные запросы, cancel, recovery, expiry и cleanup. Затем измерить холодный запуск, сетевые операции, расходы и качество результата. До этого не называть Cloud production-ready и не заменять существующий production.

Рисунки попадут в Cloud export только через явный resource manifest и проверку pixel parity. Текущий пилот отклоняет неподдержанные drawing/reference/audio сцены, чтобы не потерять их при экспорте.
